## 一、定时发送

### 状态机

```
draft ──排期──▶ scheduled ──到点──▶ running ──队列空──▶ done
  ▲                │                  │
  └──取消排期───────┘                  ├──暂停──▶ paused ──继续──▶ running
                                      └──取消──▶ canceled
```

`status` 用的是 `scheduled` 而不是原设计里的 `queued`。原因是 `queued` 已经是收件人的状态（"待发送"），
两个维度共用同一个词，面板上会分不清"任务已排期"和"这封信还没发出去"。改成 `scheduled` 之后
`theme.ts` 里可以给两套状态各自一个胶囊样式。

### 谁负责触发

`worker` 每 30 秒扫一次 `status='scheduled' AND scheduled_at <= now()`，最多同时启动 10 个。

为什么不放在 API 里：API 会重启、将来可能多副本；"到点开跑"必须由唯一常驻进程负责。
为什么不把定时任务塞进内存队列：进程重启就全丢了。库里的 `scheduled_at` 是唯一真相，
重启后自然恢复，代价只是精度取决于轮询间隔。

### 并发安全

调度器和"立即开始"按钮会抢同一条任务，用条件更新做幂等：

```sql
UPDATE campaigns SET status='running' WHERE id=? AND status='scheduled'
```

影响行数不是 1 就说明别人先领走了，直接跳过。展开收件人放在领取之后，
唯一索引 `(campaign_id, contact_id)` 再兜一层，重复触发不会重复投递。

### 三个边界

| 情况 | 处理 |
|---|---|
| 排期时分组里没人 | 直接拒绝，不让用户以为排上了 |
| 到点后分组里已无人可投 | 退回 `draft` 并清空 `scheduled_at`，不反复空跑 |
| 展开过程报错 | 同上回退，否则会永远卡在 `running` 而队列是空的 |

排期时间要求晚于当前时间至少 1 分钟，避免刚点完就被当成"已过期"处理。

## 二、A/B 测试

### 数据模型

- `campaign_variants`：一个任务最多 3 个变体，各自可覆盖主题、模板、权重
- `recipients.variant`：每条投递记录记住自己属于哪一版

变体只覆盖"主题"和"模板"两项。追踪开关、附件这些都跟模板走——把它们也做成变体，
组合数量会失控，而真实的 A/B 需求九成集中在主题上。

### 分流算法

**交织，不是分块。** 按权重先排队再切开（A A A A A B B B）比例是对的，但发信是 30 秒一封串行推进，
前 7 封全是 A、后 3 封才是 B，两组的发出时段完全不同。早上 9 点发和下午 3 点发的打开率本来就有差异，
最后得到的"A 比 B 好"可能只是时段效应。

所以用平滑加权轮询生成序列，70/30 得到 `A B A A A B A A B A`，任何前缀里的比例都贴近 7:3。
权重先按最大公约数约简，50/50 就存成 `A B` 两项循环，不会凭空生成 100 项。

### 判定

详情页给出每版的已发/打开率/点击率，并在**两版都已发出 ≥10 封**时才给"打开率更高：X"的结论。
样本不足时显示"样本不足，暂不下结论"——20 封里差 2 个打开就是 10 个百分点，
拿这种数字指导下一轮只会越跑越偏。

### 边界

- 只给 1 个变体 → 拒绝，提示"至少两个变体，单变体请直接填任务模板"
- 某个变体既没改主题也没换模板 → 拒绝，否则等于发了两遍一样的
- 变体引用的模板被删 → 退回任务主模板继续发，不让一次误删把整批信判失败
- 修改草稿的变体 = 整体替换（不是逐条 diff），避免出现"A 是旧的 50、B 是新的 30"这种不成立的组合

## 三、开放 API（已于 2026-10-26 按业务要求整条下线，见第九节）

### 令牌

格式 `mlr_` + 24 字节随机数的 base64url，约 36 字符。

- 只存 SHA-256，不存明文：备份泄漏或只读账号被盗时，明文令牌等于把整个 API 交出去
- 用 SHA-256 而不是 bcrypt：令牌本身是 24 字节随机数，没有字典攻击面，不需要刻意放慢的哈希
- `prefix` 存前 12 字符，用于在列表里认出是哪把令牌
- 明文只在创建时返回一次，之后无法取回，丢了就吊销重建

### 权限

两种：`read`（只能 GET/HEAD/OPTIONS）、`write`（读写都能）。按 HTTP 方法粗粒度划分，
不做接口级 ACL——接口数量还没到需要那套复杂度的程度。

**令牌不能管理令牌**（`SessionOnlyGuard`）。一把 write 令牌若能新建令牌，
泄漏之后就等于永久后门：攻击者自建一把新的，你把原来那把吊销也没用。所以
`/api/tokens` 只接受面板会话。

### 用法

```bash
# 建任务并立即开始（write 权限）
curl -X POST https://<站点>/api/campaigns \
  -H "Authorization: Bearer mlr_xxx" -H 'Content-Type: application/json' \
  -d '{"name":"11月回访","templateId":1,"listIds":[2]}'

curl -X POST https://<站点>/api/campaigns/12/start -H "Authorization: Bearer mlr_xxx"

# 查概览（read 就够）
curl https://<站点>/api/stats/overview -H "Authorization: Bearer mlr_xxx"
```

`last_used_at` 每分钟最多写一次。每个请求都 UPDATE 会把这张表变成写入热点，而这个字段的用途
只是"还记得这把令牌有人用"。

### 实测中发现并修掉的两个问题

## 六、第二批：周期任务 · Webhook · 软删除

> Webhook 部分已于 2026-10-26 下线，见第九节；周期任务与软删除仍在用。

### 周期任务

- 字段加在 `campaigns` 上：`recurrence`（daily/weekly/monthly）、`recurrence_interval`（1–52）、`recurrence_until`（截止）、`series_id`（指向首轮）
- **每轮跑完由 worker 复制出下一轮**，而不是原地重置：每轮的收件人在启动时才展开，投递记录和统计互不覆盖
- 只从 `status='done'` 的**最晚一轮**续期。取消（canceled）即代表用户要停，系统不会继续生成——这是刻意设计，自动续订最让人恼火的就是"取消了还来"
- 幂等：生成前检查序列里是否已存在更晚的一轮，重复扫描不会多生成
- monthly 做月末收敛：1 月 31 日 + 1 个月落在 2 月 28 日，而不是溢出到 3 月
- 列表提供「停止周期」，一次清掉整个序列的 recurrence

### Webhook

- `webhooks` + `webhook_deliveries`，事件五种：`campaign.started / done / canceled`、`contact.bounced / unsubscribed`
- 请求头带 `X-Mailer-Event` 与 `X-Mailer-Signature: sha256=HMAC-SHA256(密钥, 请求体原文)`
- 三条原则：**不阻塞发信主循环**（fire 即返回）、**失败不重试**（通知不是事务，对端按 campaignId 拉 API 兜底）、投递记录**留 7 天**可查
- 支持测试发送（同步返回对端响应）与启用开关
- 系统自检新增第 7 项「外部回调」：回调失败是典型的静默失败，必须主动暴露

### 软删除

- `campaigns` / `templates` 增加 `deleted_at`：删除先进回收站，所有常规查询（列表、详情、调度器、发送引擎、统计）一律排除
- 回收站提供「恢复」与「彻底删除」；模板仍被任务引用（含回收站里的任务）时拒绝彻底删除
- 删除确认框写清楚会失去什么、能否恢复——只问一句"确定吗"等于没问

### 第二批实测（30 项断言全过）

- 周期：首轮经假 SMTP 真实跑完 → worker 自动生成下一轮，计划时间恰为首轮 + 7 天；停止周期后整条序列 `recurrence` 清空
- Webhook：本地接收器收到真实 POST，事件名正确、HMAC 验签通过、payload 含 campaignId；停用后不再投递；投递记录可查
- 软删除：常规列表与回收站完全隔离；回收站里的任务 `start` 返回 404；恢复后回到列表；被引用模板拦下彻底删除
- 清理后回到基线：69 联系人 / 15 分组 / 6 任务 / 3 通道 / 0 回调

## 七、第三批：导入任务化（取消与断点续传）

### 为什么必须改

原来的导入是"上传 → 同步 commit"：几千行的 XLSX 在一个 HTTP 请求里解析+写库，
请求慢、会超时、没法停，进程一崩整批重来。

### 设计

- 新表 `import_jobs`，`processed_rows` 是断点游标
- worker 每轮推进 500 行；**分块处理和游标推进在同一个事务里**——
  进程崩在半路，这块要么整体生效、要么整体重来。
  联系人/分组写入全部带 `skipDuplicates`，重跑不产生脏数据（实测重启 worker 后导入数分毫不差）
- 解析结果带缓存：XLSX 解析不便宜，不能每 500 行重解析一遍
- tmp 文件清理豁免活跃任务的文件——大文件导入可能一暂停就是几个小时
- 导入进行中，worker 的空转睡眠压到 800ms（默认 3 秒一圈会把两万行拖成两分钟），
  但不会突破账号/任务的最小发送间隔

### 状态机

```
pending ──worker认领──▶ running ──队列空──▶ done
                          │ ▲
                    暂停─▶│ └─◀─继续
                          ▼
                       paused
任意未完成状态 ──▶ canceled / failed
```

pending 由 worker 认领而不是创建时就置 running：
worker 不在线时任务安静等待，worker 一启动自动接管。

### 一个语义变化

"文件内重复"的计数：同一分块内的重复照旧计入；
跨分块的重复由库内唯一约束兜住，会计入「已在库中」而不是「文件内重复」。
总数守恒（六项计数之和恒等于总行数），只是口径在极端情况下略有偏移。

### 第三批实测（25 项断言全过）

- 任务 A（2 万行）：游标 500 处暂停 → 冻结 3 秒不动 → 继续 → 完成；
  15,428 条有效邮箱全部入库、零重复；六项计数之和 = 20,000
- 任务 B（8 千行）：跑到一半 **直接重启 worker 进程** → 任务自动续跑并完成，
  6,172 条无重复无遗漏——断点续传跨进程成立
- 任务 C（8 千行）：取消后游标冻结、联系人写入停止
- 测试中发现并修掉：任务创建为 pending 但没有任何环节把它推进到 running
  （worker 认领缺失），导入永远不会开始。已修并由本测试覆盖

## 八、第四批：移除退订 · 发件账号分组 · 面板排版

### 1. 移除退订订阅

按业务要求，退订不是这套系统需要的功能，整条链路都摘掉了：

| 位置 | 处理 |
|---|---|
| `GET/POST /u/:token` 退订页 | 控制器与服务端渲染一起删除，路由变 404 |
| 邮件页脚「点此退订」 | 不再追加 |
| `List-Unsubscribe` / `-Post` 头 | 不再发送（RFC 8058 一键退订一并移除） |
| 联系人「标记退订 / 恢复订阅」 | 按钮与后端状态校验一起删除，状态只保留 subscribed / bounced / complained |
| 退订率、退订数 | 概览与接口都不再返回 |
| `contact.unsubscribed` Webhook 事件 | 从事件清单与前端选项里去掉 |
| `contacts.unsub_token` 列 | 迁移里删除 |

**数据怎么处理**：历史「已退订」的联系人状态归一为 `subscribed`；但这批地址在**抑制名单里的记录保留不动**——
它们仍然表示"不要再发给这个地址"。功能没了、界面没了，但不会因此给已经明确拒绝过的人再发信。

### 2. 发件账号分组

业务上的选择单位是「哪一批账号」，不是「第几条通道」——同一个 SMTP 账号下常有多条不同 fromName 的通道。

- 新表 `channel_groups`；`channels.group_id`（可空 = 未分组）；`campaigns.channel_group_ids`
- 接口：`GET/POST/PATCH/DELETE /channel-groups`；删除分组只解除归属（`onDelete: SetNull`），不删账号
- 任务向导第 3 步从「选通道」改为「选分组」，留空仍表示按配额自动分配
- 发送端选择顺序：**分组 > 指定通道 > 全部**。老任务只存了 `channel_ids`，继续按原样工作，不会被这次改动打断
- 发件账号页：新增分组列、分组筛选、「管理分组」（新建 / 重命名 / 删除）与表单里的分组选择

### 3. 面板排版

- 概览：首行四张卡等高（`align="stretch"` + `height:100%`）；发送趋势改为近 30 天并移到页面最底部，账号配额/联系人/近 30 天效果并成一行三张
- 联系人：左侧分组栏从 `span=6` 缩到 `span=4`（约三分之二），底部「已订阅 · 硬退信 · 抑制」并成一行
- 全站：内容区左右留白 24 → 32px，卡片内边距 24 → 28px，表格卡片统一 `4px 28px 20px`（表格不再贴边），栅格间距 16 → 24px

### 第四批实测（24 项断言全过）

- 分组：两条假 SMTP 通道只有一条在组内，按分组发送的 2 封全部走组内通道，组外通道 0 封
- 兼容：只指定 `channelIds` 的旧式任务照常发送
- 退订：`/u/` 返回 404；联系人状态写入 `unsubscribed` 被拒（400）；概览不再有退订字段；抓取的真实邮件里没有 `List-Unsubscribe`、没有退订链接
- 数据基线：69 联系人 / 15 分组 / 6 任务 / 3 通道 / 0 发件分组 / 2 模板

## 九、第五批：下线开放 API / Webhook · 多分组 · 随机间隔

### 下线

按业务判断这两套能力用不上，整条链路摘除，不做“留着但藏起来”：

| 删除项 | 说明 |
|---|---|
| `api_tokens` 表与令牌服务 | 鉴权守卫改为只认会话 Cookie，`/api/tokens` 404 |
| `webhooks` / `webhook_deliveries` 表 | 投递服务、事件推送、自检项、面板入口一并删除，`/api/webhooks` 404 |
| 事件触发点 | 任务开始/完成/取消、退信都不再 POST 外部地址 |

删的是集成能力，业务数据一条没动。

### 发件账号多分组

`channels.group_id` 改成 `group_ids` 数组：同一个发信身份可以同时属于「营销线」「通知线」等多个分组。
迁移把原有的单分组平移进数组，没有丢归属。删除分组时用 `array_remove` 把 id 从每条通道的数组里摘掉，
通道本身不受影响。

发送端按分组解析的逻辑不变：分组 > 指定通道 > 全部，只要通道的任一分组命中任务选择即可。

### 随机发送间隔

任务新增 `send_interval_max_sec`。填了最大间隔后，每封之间在 `[最小, 最大]` 内随机：

- 随机值**每发一封重抽一次**并缓存，整个等待期用同一个目标值。
  如果每次 tick 都重抽，实际间隔会被不断推高到区间上限（等于退化成最慢节奏）
- 不填最大间隔就是原来的固定间隔，老任务行为不变
- 最大 < 最小直接 400，前端也会拦
