# 运维手册

系统跑起来之后，日常只有三件事：**看配额、查告警、处理退信**。这份文档按"出问题时怎么定位"组织，而不是按功能罗列。

---

## 一、每天早上看三件事

打开 `https://mail.example.com` 的概览页：

| 看什么 | 正常 | 不正常时 |
|---|---|---|
| 今日剩余配额 | 还有余量 | 显示 0 → 今天的任务会等到明天自动续；显示红色数字 → 所有账号都满了 |
| 顶部告警区 | 不出现 | 每条告警都带处置建议，按提示做 |
| 待发队列 | 0，或正在减少 | 有数字但长时间不动 → 见下面「队列不动」 |

**不需要每天做的**：备份、证书续期、日志轮转，都是 cron 和 systemd 在管。只有在「系统运维」页出现黄色/红色项时才需要介入。

## 二、发不出去：按现象分诊

### 队列有积压但不减少

按这个顺序查，一步排除一个原因：

```bash
# 1. 发送进程活着吗（面板"系统运维"页也有，这里给命令行版）
systemctl is-active mailer-worker
journalctl -u mailer-worker -n 30 --no-pager -o cat

# 2. 心跳还有没有（超过 3 分钟没更新说明主循环卡住了）
sudo -u postgres psql mailer -c "select key, value, updated_at from system_state"

# 3. 有没有可用账号（status 不是 active 就不会被调度）
sudo -u postgres psql mailer -c "select id,name,status,daily_limit,sent_today,quota_date from channels"

# 4. 队列里到底是什么状态
sudo -u postgres psql mailer -c "
  select status, count(*), min(next_attempt_at), max(next_attempt_at)
  from recipients group by status"
```

最常见的三个原因：**配额用完**（等次日）、**所有账号被自动停用**（看 `last_error`）、**worker 没起**。

### 全部失败，错误码 EAUTH

密码或授权码错了。QQ/163 必须用「授权码」而不是登录密码；企业邮箱改过密码后，面板里存的还是旧的。到「发件账号」页点「测试连接」，会直接告诉你认证是否通过。

### 部分失败，错误码是 4xx / 5xx

| 码 | 含义 | 系统怎么处理 |
|---|---|---|
| 4xx | 临时失败（对方限流、邮箱满） | 退避重试 3 次（1 / 5 / 30 分钟），之后判死 |
| 5xx | 永久失败（地址不存在） | **立刻判死并进抑制名单**，不再浪费配额 |

真实退信是**异步**的——服务商先回 250，几分钟后才退信回来。这些由 worker 每 10 分钟轮询一次收件箱，自动解析并加入抑制名单。

### 发出去了但进垃圾箱

这不是程序问题，检查顺序是域名认证 → 内容 → 发送历史：

```bash
# SPF / DKIM / DMARC 是否齐全
dig +short TXT example.com
dig +short TXT s1._domainkey.example.com
dig +short TXT _dmarc.example.com
```

三项缺一不可。另外**同一账号一天发太多、内容里链接过多、带附件**，都会显著拉低进箱率——但这些都是运营策略，不是代码能修的。

## 三、备份与恢复

每天 03:15 自动备份到 `/var/backups/mailer`，保留 14 天。备份完会往 `system_state` 写一条 `last_backup_at`，面板据此判断"备份是不是真的跑了"。

**日志在 `/var/log/mailer-backup.log`。** 以前这里重定向到 `/dev/null`，结果 cron 的 `PATH` 缺少 `/usr/sbin` 导致 `runuser: command not found`，备份连着几天没跑成也没人知道——目录里只留一个 0 字节的 `.part` 文件。现在失败会写清楚原因。

手动验证一次（**要用 cron 的环境**，否则测不出这类问题）：

```bash
env -i PATH=/usr/bin:/bin HOME=/root /usr/local/sbin/mailer-backup
tail -20 /var/log/mailer-backup.log
```

### 验证备份可用（建议每月一次）

```bash
sudo mailer-restore
```

它会恢复到一个临时库、核对表数量与关键表行数、然后删掉临时库，**不碰生产数据**。

### 真要恢复

```bash
# 1. 先停服务，避免恢复过程中还在写
sudo systemctl stop mailer-api mailer-worker

# 2. 恢复（会先自动备份当前库到 pre-restore-*.dump 作为回滚点）
sudo mailer-restore --live /var/backups/mailer/db-20261026-0315.dump

# 3. 起服务
sudo systemctl start mailer-api mailer-worker
```

回滚就是用 `pre-restore-*.dump` 再恢复一次。

## 四、证书

用的是 Let's Encrypt **IP 证书**，有效期只有 **6 天**（LE 对 IP 证书强制 `shortlived` 档案，不是配置问题）。

- 续期：`/etc/cron.d/mailer-certbot` 每天 03:17 / 15:17 检查
- 续期后：`mailer-cert-hook` 会把证书副本同步到 `/opt/mailer/shared/certs/`（面板要读它），然后 reload nginx
- 手动续期：

```bash
sudo /opt/certbot/bin/certbot renew --deploy-hook /usr/local/sbin/mailer-cert-hook
```

**面板显示的天数持续减少 = 续期失败**，去 `/var/log/letsencrypt/letsencrypt.log` 看原因。证书真过期了浏览器会直接拦截，届时 HTTPS 打不开，但邮件发送不受影响（发信走的是邮箱服务商的服务器，不是这台机器）。

## 五、升级与回滚

```bash
# 升级
cd /opt/mailer
sudo -u mailer git pull            # 或者用新代码包覆盖
sudo -u mailer pnpm install
sudo -u mailer pnpm -r build
sudo -u mailer bash -c 'set -a; . /etc/mailer/mailer.env; set +a; cd apps/api && pnpm exec prisma migrate deploy'
sudo systemctl restart mailer-api mailer-worker

# 确认起来了
systemctl status mailer-api mailer-worker --no-pager
curl -s https://127.0.0.1/api/health -k
```

`prisma migrate deploy` 只跑未应用的迁移，不会重置数据。**不要用 `migrate dev`**（那是开发用的，会尝试建影子库）。

回滚代码：`git checkout <上一个 tag>` 后重新 build。数据库迁移原则上不做回滚——新增表和字段都是向后兼容的。

## 六、加账号 / 扩容

在「发件账号」页添加。选择服务商会自动填好 host/port/加密方式。

**必须先说清楚的**：同一个邮箱账号拆成多条通道记录，**不会提升服务商侧的真实配额**。对方按账号限流，不看你本地有几条记录。系统现在按真实账号（SMTP 服务器 + 用户名）聚合配额与发送间隔：多条通道只代表不同发信身份，共用一本账，不会再出现「3 条通道 = 150 封/天」的错觉。

真实扩容只有两条路：

1. **加更多邮箱账号**（每个账号日发 50 封左右，看服务商政策）
2. **改用事务邮件 API**（阿里云 / 腾讯云 / SendCloud 等），进箱率和量级都更好，但要自己的发信域名和实名认证

日发量 ≈ **真实邮箱账号数** × 单账号日配额。当前面板里有 3 条通道，但它们共用 1 个邮箱账号，因此真实上限是 **1 × 50 = 50 封/天**，不是 150。要提升到 150，需要再准备 2 个真实邮箱账号，而不是再复制 2 条通道记录。

## 七、定时发送 / A/B / 周期任务

### 定时任务没有到点启动

调度器跑在 **worker** 里，API 不负责触发——所以先确认 worker 活着：

```bash
# 1. 发送进程在不在
systemctl is-active mailer-worker

# 2. 有没有到点却没被领走的任务
sudo -u postgres psql mailer -c \
  "select id,name,status,scheduled_at from campaigns where status='scheduled' order by scheduled_at"

# 3. 调度日志（每 30 秒一轮，到点会打印"定时任务已启动"）
journalctl -u mailer-worker -n 100 --no-pager -o cat | grep -E "定时|调度"
```

常见原因只有三个：worker 没起、时间还没到（检查间隔 30 秒，不是精确到秒）、
到点时分组里已经没人（任务会被自动退回草稿，日志里有 `已退回草稿`）。

### A/B 结果怎么看

详情抽屉里的「A/B 对比」在两版各发出 ≥10 封之前只显示"样本不足，暂不下结论"。
数字直接来自投递表，可以单独核对：

```sql
select variant, status, count(*) from recipients
where campaign_id=<id> group by 1,2 order by 1,2;
```

## 八、故障对照表

| 发送进程每几十秒重启一次 | `imapflow` 在 socket 超时时 emit('error')，没有监听者时 Node 直接终止进程；systemd 只看到 exit-code | 已在 `bounce.service.ts` 挂 error 监听器降级为告警；`worker.ts` 增加 uncaughtException 兜底并打印堆栈。查看 `journalctl -u mailer-worker` 里的「IMAP 连接异常」即为已降级 |
| 现象 | 大概率原因 | 处理 |
|---|---|---|
| 面板打不开 | nginx 或 api 挂了 | `systemctl status nginx mailer-api` |
| 面板能开但一直转圈 | api 起了但连不上数据库 | `journalctl -u mailer-api -n 50` |
| 登录后立刻被踢回登录页 | 会话过期或 `JWT_SECRET` 被改 | 重新登录；改过密钥的话所有会话都会失效 |
| 队列不动 | 配额用完 / 账号全停用 / worker 挂了 | 见第二节分诊 |
| 任务卡在"发送中" | worker 崩在发送途中 | 2 分钟后自动回收重发，可能重复一封 |
| 邮件重复到达 | at-least-once 语义 | 正常；同一任务不会重复，只有进程崩溃时在途的那封会 |
| 打开率一直是 0 | 收件人用了纯文本客户端 / 图片被拦 | 正常现象，打开追踪本身就不精确 |
| 某人还能收到 | 任务是更早建的，收件人已展开 | 建任务时就固定了收件人；要立刻停发，把他移出所有分组并加入抑制名单 |
| 备份项报错 | cron 没跑 / 磁盘满 | `ls -l /var/backups/mailer`、`df -h` |
| 证书项报错 | 续期失败 | 见第四节 |

## 九、几个不要做的事

- **不要开服务器的 25 端口入站**。发信全走邮箱服务商的 465/587，25 端口开着只会招来扫描。
- **不要手动改数据库里的 `password_enc`**。它是 AES-256-GCM 密文，密钥在 `/etc/mailer/mailer.env` 的 `CRED_KEY`。
- **不要更换 `CRED_KEY`**，除非准备把所有发件账号的密码重新录入一遍——旧密文将永久无法解密。
- **不要删有投递历史的联系人**。系统会拦截，因为删了会让任务统计凭空少一批数据；要停发就把他移出所有分组，或加入抑制名单。
- **不要用 `prisma migrate reset`**，那会清空整个数据库。
